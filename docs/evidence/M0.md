## 开发中发现并修复的问题

链接脚本最初把 `.bss` 标为 `(NOLOAD)`，ld.lld 因此没有把 `.bss` 放进任何 `PT_LOAD`。
内核仍能启动，因为它自己清零 BSS；但 GRUB 不知道这段内存存在，后续加载模块可能覆盖启动栈。
现已去掉 `(NOLOAD)`，`.bss` 位于独立的 RW `PT_LOAD`。`check_elf.py` 目前**不检查** BSS 是否被 LOAD 覆盖（见限制）。

## 已知限制

- `.deb`、`tools/grub/extracted/`、`env-check/*.iso|*.o` 不纳入 git（见 .gitignore），按 README 重建。
- 没有使用 isa-debug-exit。成功的内核停机后，运行器在 1 s 宽限期后自行终止 QEMU。
- 用例 5 是「正常镜像 + 不存在的标记」，用来验证超时路径；没有专门的「内核启动但不打印 BOOT_OK」镜像。
- ISO 只支持 BIOS（i386-pc）启动，不含 EFI。
- 没有 VGA 输出（属于 M1）；GRUB 菜单与内核输出都走串口。
- 启动栈没有哨兵或 guard page。
- 构建不追求字节级可复现；只记录工具版本。

## M0 收尾（2026-11-10，提交 `811e417`）

在 M1 开始之前补做，正常启动路径不变。

- **PT_LOAD 覆盖检查**：check_elf.py 直接解析 ELF32 节头与程序头。每个非空的 SHF_ALLOC 节都必须落在某个 PT_LOAD 的内存范围内；
  有文件内容的节还必须落在该段的文件范围内，且偏移一致；NOBITS（.bss）只按内存范围判断。判断依据是地址范围，不检查脚本里是否写了 `NOLOAD`。
- **负向用例 neg-elf-noload-bss**：同一批目标文件改用 `.bss (NOLOAD)` 链接，检查器必须拒绝。实测只有 `alloc-sections-loaded` 一项 FAIL，并指出 `.bss`。
- **BOOT_FAIL 路径**：测试专用入口 `selftest_bad_magic_entry`（tests/kernel/bad_magic_entry.asm，用 `--entry` 链接成 build/test/bad-magic.elf）
  以 EAX=0xDEADBEEF 跳到真正的 `_start`。用例 boot-fail-bad-magic 要求出现 `BOOT_FAIL bad multiboot magic 0xdeadbeef`、不出现 BOOT_OK、QEMU 保持存活。**PASS**。
  build/kernel.elf 不含该入口（nm 计数 0），入口仍是 `_start`。
- **Git 基线**：M0 `c64cb9b`、`6485a0a`；收尾 `811e417`。`build/`、`.deb`、`tools/grub/extracted/`、`env-check/*.iso|*.o` 不纳入 git。没有远端仓库。

## 三个学习问题（MILESTONES M0）

1. **谁装载内核？** 提示：按顺序看 SeaBIOS → ISO 引导（El Torito）→ GRUB 读取 `boot/grub/grub.cfg` → `multiboot` 命令按 ELF 的 `PT_LOAD` 把段复制到物理地址。对照 `readelf -l build/kernel.elf`，并思考：`.bss` 为 NOLOAD 时会发生什么？
2. **初始栈在哪里？** 提示：看 docs/context.md 和 build/kernel.map。为什么 GRUB 交给内核时 ESP 不可用？为什么 `call` 之前要先 `sub esp, 8`？
3. **为什么不能链接宿主启动文件？** 提示：宿主的 crt1.o/crti.o 和 libc 是 aarch64 Linux 用户态代码，依赖内核 syscall、动态加载器和 `main`；这里没有操作系统，CPU 架构也不同。哪些编译、链接参数分别阻止了它们进入镜像？用例 1 中哪几项检查能发现这类错误？
